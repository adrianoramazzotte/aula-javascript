Plano de desenvolvimento em 10 etapas

Este documento existe para responder a uma pergunta específica: “voltei ao projeto depois de duas semanas — o que eu faço agora?” Cada etapa traz objetivo, pré-requisitos, passos na ordem de execução, comandos, arquivos a criar e um critério objetivo de conclusão.

    Antes de tudoComo usar este plano

    Três documentos governam o projeto, e cada um responde a uma pergunta diferente. Confundi-los é a forma mais rápida de se perder.

    Rotina ao retomar o projeto

    1. Leia PROGRESSO.mdEle diz qual é a etapa corrente e o que ficou pela metade. É a primeira coisa a abrir, sempre.
    2. Abra a etapa correspondente neste planoCada etapa é autocontida: você não precisa reler as anteriores para trabalhar na atual.
    3. Confirme que o ambiente sobedocker compose up -d e npm run start:dev. Se não subir, resolver isso é a tarefa — não avance por cima de ambiente quebrado.
    4. Rode os testes antes de escrever códigoSaber se a suíte já estava vermelha ao chegar evita horas caçando um defeito que não é seu.
    5. Trabalhe na próxima tarefa não marcadaUma tarefa por vez, um commit por tarefa concluída.
    6. Ao encerrar, atualize PROGRESSO.mdMarque o que concluiu e escreva em uma linha onde parou. Este passo é o que torna a retomada possível — não o pule por estar com pressa.
    Onde o código vai morar

    O sistema será desenvolvido na pasta mercado/ deste mesmo repositório, aproveitando as branches dev, hml e main e a proteção já configuradas. O material didático continua onde está; nada se mistura.

    A alternativa é um repositório separado — mais limpo em um projeto profissional, porém exige refazer branches, proteção e acessos dos alunos. Se optar por separar, o único trecho deste plano que muda é o passo 1 da etapa 0.

    Banco de dados

    • synchronize: false sempre, em todos os ambientes. Toda alteração de esquema é uma migração versionada.
    • Nome da migração descreve a intenção: 1712000000000-CreateUsersTable.ts.
    • Migração nunca é editada depois de aplicada em hml ou main — corrige-se com uma nova.
    • Toda migração tem down() funcional, testado ao menos uma vez.
    • Dinheiro em DECIMAL(10,2), com transformador explícito no TypeORM para virar número.

    Código

    • TypeScript em modo strict. any exige comentário justificando.
    • Regra de negócio mora no service. Controller só recebe, valida e devolve.
    • Toda entrada passa por DTO com class-validator; ValidationPipe global com whitelist e forbidNonWhitelisted.
    • Nada de consulta sem paginação em rota de listagem.
    • Nome de variável e função em inglês; comentário e mensagem ao usuário em português.

    Definição de pronto de uma tarefa

    • Critérios de aceite do requisito atendidos.
    • Teste de unidade na regra de negócio e teste de integração no caminho principal.
    • Verificação de permissão testada, inclusive a tentativa de acessar recurso de outro dono.
    • npm run lint e npm test passando.
    • PROGRESSO.md atualizado.

    Etapa 0Fundação

    Objetivo: ter um projeto que sobe, conecta no banco e roda no CI — antes de qualquer regra de negócio.

    Entregável: GET /health retornando 200 com o estado da conexão com o banco.

    Passos

    1. Criar o projeto Na branch dev, criar a pasta mercado/ com o Nest CLI.
    2. Instalar as dependências de base Configuração, TypeORM, driver MySQL e validação.
    3. Subir MySQL e Redis em Docker Um docker-compose.yml com os dois serviços e volume nomeado para os dados não sumirem.
    4. Configuração tipada por ambiente ConfigModule global validando as variáveis na inicialização. Faltando variável obrigatória, a aplicação não sobe — falha cedo e explícita.
    5. TypeORM com synchronize: false Um data-source.ts exclusivo para o CLI de migrações e os scripts migration:generate, migration:run e migration:revert no package.json.
    6. Primeira migração Criar a tabela users. É o teste real de que a cadeia entidade → migração → banco funciona.
    7. Endpoint /health Executa SELECT 1 e devolve o estado. É o que o provedor de nuvem vai consultar depois.
    8. Qualidade e CI ESLint, Prettier, Jest configurado e um workflow do GitHub Actions rodando lint, teste e build em todo push.

    • mercado/.env.example — todas as variáveis, sem valores reais
    • mercado/src/config/ — configuração tipada e validação de ambiente

    Concluída quando

    • docker compose up -d sobe banco e Redis sem erro.
    • npm run migration:run cria a tabela users em um banco vazio.
    • npm run migration:revert desfaz a migração sem deixar resíduo.
    • GET /health devolve 200; com o banco derrubado, devolve 503.
    • O CI está verde no GitHub.
    • .env está no .gitignore e nenhum segredo foi versionado.
    A armadilha desta etapa

    É tentador ligar synchronize: true “só para começar rápido”. Quem faz isso descobre, três semanas depois, que precisa gerar a primeira migração a partir de um banco que já divergiu — e que uma coluna com dados de teste sumiu numa reinicialização. Configure migrações agora, quando custa quinze minutos.

    Etapa 1Identidade e acesso

    Objetivo: cadastrar usuários, autenticar com JWT e proteger rotas por papel.
    Requisitos: RF-01, RNF-01.1 a 01.11.
    Pré-requisito: etapa 0 concluída.

    Passos

    1. EntidadesUser (com role e status), RefreshToken e Address, cada uma com sua migração.
    2. Hash de senhaArgon2id em um serviço isolado. A senha nunca aparece em log, em resposta de API ou em fixture de teste.
    3. Cadastro e verificação de e-mailToken de uso único com 24 h de validade. O envio pode ser um log no console nesta etapa — o provedor real entra na etapa 7.
    4. Login e emissão de tokensAccess de 15 min e refresh de 7 dias, com o hash do refresh guardado no banco.
    5. Rotação e detecção de reusoCada uso do refresh invalida o anterior. Reapresentação de token já usado derruba todas as sessões do usuário.
    6. Guards e decoratorsJwtAuthGuard, RolesGuard, @Roles() e @CurrentUser() em src/common/. Serão usados em todas as etapas seguintes.
    7. Recuperação de senhaToken de 1 h, invalidado no uso. A resposta é idêntica para e-mail existente e inexistente, para não revelar quem tem conta.
    8. Limitação de tentativas@nestjs/throttler global, com limite mais rígido em login, cadastro e recuperação.
    9. Seed do administradorUm script cria o primeiro admin a partir de variáveis de ambiente. Admin não se cadastra pela interface.

    Concluída quando

    • Cadastro com e-mail repetido devolve 409.
    • Login devolve o par de tokens; /auth/refresh rotaciona e invalida o anterior.
    • Reusar um refresh token já consumido derruba todas as sessões — com teste automatizado.
    • Rota anotada com @Roles('admin') devolve 403 para comprador autenticado.
    • Seis tentativas de login erradas em sequência devolvem 429.
    • Nenhuma resposta da API contém password_hash.

    Etapa 2Lojas e catálogo

    Objetivo: vendedor com loja aprovada publica produtos com variações e imagens.
    Requisitos: RF-02, RF-09.1 a 09.4.
    Pré-requisito: etapa 1 — o dono do recurso vem do token.

    Passos

    1. Entidades do domínioStore, Category (auto-relacionada), Product, ProductVariant e ProductImage, com as migrações e os índices de slug, status e chaves estrangeiras.
    2. Abertura e aprovação de lojaSolicitação pelo comprador, fila de aprovação para o administrador, mudança de papel para seller na aprovação.
    3. Guard de dono do recursoStoreOwnerGuard compara o storeId do token com o do recurso acessado. Toda rota de vendedor passa por ele.
    4. CRUD de produtoCriação em rascunho, edição, exclusão lógica e listagem restrita à própria loja.
    5. VariaçõesSKU único, atributos em JSON, preço e estoque próprios. Produto sem variação ganha uma variação padrão implícita — decidir isso aqui evita dois caminhos de código no checkout.
    6. ImagensUpload para armazenamento de objetos, conversão para WebP e geração de miniatura com sharp. Nada gravado no disco do servidor de aplicação.
    7. Publicação validadaA transição rascunho → publicado só ocorre com título, imagem, preço maior que zero, categoria e loja aprovada. A mensagem de erro aponta o campo pendente.
    8. Seed de categoriasUma árvore inicial de categorias, para não travar o desenvolvimento das próximas etapas.

    Concluída quando

    • Vendedor da loja A recebe 403 ao editar produto da loja B — com teste automatizado.
    • Produto sem imagem não publica, e o erro diz qual campo falta.
    • Loja pendente não consegue publicar produto.
    • Upload devolve URL pública funcional, com miniatura gerada.
    • Exclusão de produto é lógica: some da listagem, permanece consultável por id.

    Etapa 3Vitrine SSR e SEO

    Objetivo: páginas públicas renderizadas no servidor, encontráveis por busca.
    Requisitos: RNF-04 completo, RF-02.2 e 02.7.
    Pré-requisito: etapa 2 — é preciso ter produto publicado para exibir.

    Passos

    1. Motor de viewsConfigurar Handlebars no main.ts, com layout base, partials de cabeçalho e rodapé, e helpers de formatação de moeda e data.
    2. Rotas públicas/ (vitrine), /c/:slug (categoria), /produto/:slug e /loja/:slug, em um módulo web separado dos controllers de API.
    3. Busca e filtrosÍndice FULLTEXT em título e descrição; filtros por categoria, faixa de preço, loja e nota; ordenação e paginação — sempre com limite máximo.
    4. SlugsGerados do título, únicos, imutáveis após a publicação. Mudança de título mantém o slug antigo para não quebrar links já indexados.
    5. Metadados<title> e description únicos por página, Open Graph, Twitter Card e canonical em páginas filtradas ou paginadas.
    6. Dados estruturadosJSON-LD de Product, Offer, AggregateRating e BreadcrumbList na página de produto.
    7. Sitemap e robots/sitemap.xml gerado dos produtos publicados e /robots.txt bloqueando carrinho, checkout, conta e área administrativa.
    8. Imagens responsivassrcset, dimensões explícitas para não gerar deslocamento de layout, e carregamento diferido abaixo da dobra.

    Concluída quando

    • curl na página de produto devolve HTML com título, preço e descrição — sem executar JavaScript.
    • A URL é /produto/tenis-corrida-azul-42, não /produto?id=7311.
    • O validador de dados estruturados do Google aceita a página sem erro.
    • /sitemap.xml lista apenas produtos publicados.
    • Lighthouse na página de produto: SEO ≥ 90 e desempenho ≥ 80 com dados de exemplo.
    • A vitrine é usável em tela de 360 px, sem rolagem horizontal.

    Etapa 4Carrinho

    Objetivo: carrinho persistente, com itens de várias lojas, que sobrevive ao login.
    Requisitos: RF-03.
    Pré-requisito: etapa 3 — o botão de comprar nasce na página de produto.

    Passos

    1. EntidadesCart (com user_id nulo ou session_id) e CartItem, com restrição de unicidade por carrinho e variação.
    2. Sessão de visitanteIdentificador em cookie HttpOnly, Secure e SameSite=Lax, criado na primeira adição ao carrinho.
    3. OperaçõesAdicionar, alterar quantidade, remover e esvaziar — sempre validando existência, publicação e estoque da variação.
    4. Mesclagem no loginAo autenticar, o carrinho do visitante é incorporado ao da conta: mesma variação soma quantidades, respeitando o estoque disponível.
    5. Revalidação a cada exibiçãoPreço e disponibilidade vêm do banco. Mudança desde a inclusão gera aviso explícito antes de seguir para o checkout.
    6. Agrupamento por lojaA resposta e a tela agrupam por loja, cada grupo com subtotal e frete próprios.
    7. Frete por tabelaTabela por região configurada por loja, mais opção de retirada. Integração real com transportadora está fora do MVP.
    8. ExpiraçãoRotina que remove carrinhos de visitante sem atividade há 30 dias.

    Concluída quando

    • Adicionar como visitante, fazer login e encontrar o item lá — com teste automatizado.
    • Requisição com preço adulterado no corpo é ignorada: o valor usado é o do banco.
    • Carrinho com itens de duas lojas mostra dois subtotais e dois fretes.
    • Produto despublicado depois de adicionado aparece marcado e bloqueia o checkout.
    • Quantidade acima do estoque é rejeitada com mensagem clara.

    Etapa 5Checkout e pagamento marco

    Objetivo: transformar carrinho em pedido pago, com estoque baixado corretamente.
    Requisitos: RF-04 completo, RF-05.1 a 05.4.
    Pré-requisito: etapa 4 e conta de teste no gateway já criada.

    Esta é a etapa que define o projeto

    Ao final dela existe um sistema que vende. Reserve mais tempo do que parece necessário: é aqui que moram concorrência, transação, integração externa e processamento assíncrono — os quatro assuntos difíceis do projeto, todos juntos.

    Passos

    1. EntidadesOrder, SubOrder, OrderItem, Payment e OrderStatusHistory. OrderItem guarda snapshot de título e preço unitário.
    2. Fluxo do checkoutIdentificação, endereço, frete por loja, resumo e pagamento — cada passo validado no servidor, sem confiar no estado do cliente.
    3. Criação transacional do pedidoEm uma única transação: criar pedido, criar um subpedido por loja, gravar itens e reservar estoque com SELECT ... FOR UPDATE na variação. Falhou qualquer parte, tudo volta atrás.
    4. Idempotência na entradaChave de idempotência única por tentativa de checkout: duplo clique devolve o mesmo pedido, não cria outro.
    5. Integração com o gatewayCartão tokenizado no navegador; a API recebe só o token. Pix devolve o código de pagamento. Nenhum dado de cartão passa pelo servidor.
    6. WebhookVerificar a assinatura, registrar o payload bruto, checar se o evento já foi processado e só então confirmar. Em desenvolvimento, expor o endereço local com ngrok.
    7. ConfirmaçãoAprovado o pagamento: efetivar a baixa de estoque, calcular comissão e líquido por subpedido, mover para pago e registrar no histórico.
    8. Expiração da reservaTarefa a cada 5 minutos cancela pedidos não pagos há mais de 30 minutos e devolve o estoque — sempre reconferindo se o pagamento não entrou nesse intervalo.
    9. Testes do caminho críticoCompra completa de ponta a ponta; webhook duplicado; e duas compras simultâneas da última unidade.

    Concluída quando

    • Uma compra completa funciona de ponta a ponta com o gateway em modo de teste.
    • Reenviar o mesmo webhook não confirma o pedido duas vezes nem baixa o estoque duas vezes.
    • Duas requisições simultâneas pela última unidade: uma conclui, a outra recebe erro — e o estoque nunca fica negativo.
    • Pedido não pago é cancelado pela rotina e o estoque volta.
    • Mudar o preço do produto depois da compra não altera o valor do pedido já criado.
    • Nenhum dado de cartão aparece no banco ou nos logs.

    Etapa 6Operação do vendedor

    Objetivo: fechar o ciclo operacional — o vendedor separa, envia e o comprador acompanha.
    Requisitos: RF-05.1 a 05.6, RF-09.5 a 09.8.
    Pré-requisito: etapa 5 — só há o que operar se houver pedido pago.

    Passos

    1. Máquina de estadosUm serviço central valida cada transição contra o mapa da especificação. Transição inválida lança exceção; a interface apenas reflete o que o serviço permite.
    2. Painel do vendedorLista de subpedidos por estado, detalhe com itens e endereço, ações de avançar estado e campo de código de rastreio.
    3. Linha do tempo do compradorHistórico de cada subpedido, com data, estado e rastreio quando houver.
    4. Cancelamento e devoluçãoCancelar só antes do envio; depois disso o caminho é devolução, com estorno via gateway e reversão de comissão e estoque.
    5. Estoque do vendedorTela de ajuste de estoque por variação e alerta de estoque baixo.
    6. ExtratoPor período: pedidos, valor bruto, comissão retida e líquido a receber.

    Concluída quando

    • Tentar pular de pago direto para entregue é rejeitado pelo serviço — com teste automatizado.
    • Vendedor A não enxerga nem altera subpedido da loja B.
    • Cancelamento devolve o estoque e reverte a comissão.
    • Todo estado registra autor, data e motivo no histórico.
    • O extrato bate com a soma dos subpedidos do período.

    Etapa 7Reputação e notificações

    Objetivo: avaliações confiáveis e comunicação automática com as duas pontas.
    Requisitos: RF-06 e RF-08 completos.
    Pré-requisito: etapa 6 — só avalia quem recebeu.

    Passos

    1. Avaliação verificadaVínculo com order_item_id único: só avalia quem comprou aquele item e cujo subpedido está entregue. Uma avaliação por item.
    2. Média desnormalizadaRecalcular e gravar média e contagem em produto e loja a cada avaliação. A vitrine lê o campo pronto, nunca agrega em tempo real.
    3. Resposta e moderaçãoUma resposta pública por avaliação; denúncia por qualquer usuário; fila de moderação para o administrador ocultar.
    4. Infraestrutura de filaBullMQ sobre Redis, com repetição em espera exponencial, no máximo 3 tentativas e fila de fracassos.
    5. E-mail transacionalProvedor real (Resend, SendGrid ou SES) e templates versionados. Migrar para cá os e-mails simulados da etapa 1.
    6. Push PWAChaves VAPID, inscrição pelo service worker, entidade push_subscriptions e remoção automática de inscrição inválida (410).
    7. Momento de pedir permissãoSolicitar autorização de push depois de uma ação relevante — como concluir uma compra — nunca ao abrir o site.
    8. PreferênciasPor canal e por tipo de evento. Avisos de segurança e de transação não são desativáveis.
    9. Isolamento de falhasErro de envio nunca derruba operação de negócio: o pedido se confirma mesmo que o e-mail falhe.

    Concluída quando

    • Quem não comprou não consegue avaliar — com teste automatizado.
    • Avaliar duas vezes o mesmo item de pedido é rejeitado.
    • A média do produto muda ao registrar nova avaliação.
    • Derrubar o provedor de e-mail não impede a confirmação de um pedido.
    • Push chega ao vendedor em uma venda real de teste.
    • Desativar um tipo de notificação interrompe aquele envio e só aquele.

    Etapa 8Administração e relatórios

    Objetivo: dar ao operador da plataforma visão e controle.
    Requisitos: RF-07 completo, RF-09.4 e 09.7.
    Pré-requisito: etapa 6 — relatório sem dado real não se valida.

    Passos

    1. Área administrativaRotas sob /admin, protegidas por papel e excluídas da indexação no robots.txt.
    2. Visão geralGMV, comissão apurada, número de pedidos, ticket médio e taxa de cancelamento, com filtro de período.
    3. Relatórios detalhadosVendas por período com comparação, produtos mais vendidos, curva ABC por faturamento, ranking de vendedores e painel operacional de pedidos parados.
    4. ModeraçãoFilas de lojas pendentes, avaliações denunciadas e produtos sinalizados, cada uma com ação em um clique.
    5. GestãoBloqueio de usuário, alteração de papel, suspensão de loja e ajuste de comissão global ou por loja — tudo registrado em auditoria.
    6. ExportaçãoCSV em todo relatório, gerado em fila quando o volume exigir.
    7. Desempenho das consultasÍndices por data e por loja. Acima de 50 mil pedidos, tabela de agregados diários alimentada por rotina.

    Concluída quando

    • Comprador e vendedor recebem 403 em qualquer rota /admin.
    • O GMV do relatório bate com a soma manual dos pedidos pagos do período.
    • Alterar o preço de um produto não altera o faturamento de meses anteriores.
    • Suspender uma loja despublica seus produtos e preserva os pedidos em andamento.
    • O CSV abre corretamente com acentuação e separador de decimais brasileiros.

    Etapa 9PWA, desempenho e produção

    Objetivo: transformar a aplicação que funciona em aplicação pronta para uso real.
    Requisitos: RNF-02, RNF-03 e RNF-04.8 a 04.10.
    Pré-requisito: etapas 0 a 8 concluídas.

    Passos

    1. PWAmanifest.webmanifest com ícones de 192 e 512 px, service worker com cache de casca e estáticos, e página offline.
    2. Regra de cacheEstáticos com cache-first; carrinho, checkout, conta e pedidos sempre da rede. Preço em cache é defeito grave.
    3. Auditoria de consultasLigar o log de SQL e percorrer as telas principais caçando N+1. Corrigir com relations ou join explícito.
    4. Índices e desempenhoRevisar o plano de execução das consultas mais frequentes e criar os índices faltantes.
    5. Teste de cargak6 ou Artillery simulando 200 usuários simultâneos e 50 pedidos por minuto, medindo o p95.
    6. Endurecimento de segurançahelmet, CSP restritiva, CSRF nos formulários SSR, revisão dos limites de requisição e npm audit zerado em vulnerabilidades altas.
    7. AcessibilidadeNavegação completa por teclado, foco visível, contraste conferido e leitura com leitor de tela nas telas de compra.

    A linha mais importante do arquivo

    É a “Parei em”. Marcar caixinhas diz o que foi feito; essa linha diz o que estava acontecendo na cabeça de quem escreveu o código. Sem ela, retomar custa uma hora de leitura para reconstruir o contexto — e essa hora se paga em cada interrupção do projeto.

    Quando uma etapa termina

    1. Rodar npm run lint e npm test — tudo verde.
    2. Percorrer a lista “Concluída quando” da etapa, item por item, executando de fato cada verificação.
    3. Atualizar PROGRESSO.md.
    4. Commit e push em dev.
    5. Promover para hml e validar no ambiente de homologação.
    6. Só então começar a etapa seguinte.

    Se algo der errado no meio

    Encontrou um defeito de uma etapa anterior? Corrija na hora, com commit próprio do tipo fix, e registre em PROGRESSO.md. Não abra uma lista paralela de pendências: lista de dívida técnica que ninguém lê é dívida que ninguém paga.

    Descobriu que um requisito da especificação está errado ou incompleto? Atualize a especificação antes de implementar diferente. Código que diverge do documento sem que o documento mude é a origem mais comum de discussão sobre o que havia sido combinado.
