    Projeto escolhido — e redefinido

    Esta foi a opção escolhida para desenvolvimento, mas com escopo redefinido: em vez do PDV para minimercado físico descrito abaixo, será construído um marketplace de e-commerce multivendedor. A especificação que guia o desenvolvimento está em Especificação · Mercado. Esta página permanece como o estudo de contexto que originou a escolha.

    Seção 01O problema

    O minimercado ganha centavos por item e perde reais por descuido. A margem líquida do setor gira em torno de 2% — não há espaço para produto vencido nem para gôndola vazia.

    O dono do mercadinho conhece o próprio negócio de cor, mas conhece de memória. Ele sabe que arroz sai bem, sabe que o iogurte encalha, sabe quem deve fiado. O que ele não sabe é quanto: quantos pacotes de arroz venderam na terça, quantos litros de leite venceram no mês passado, qual fornecedor entrega mais caro que o concorrente. Sem número, a compra é feita pelo susto — compra-se demais do que acabou de faltar e de menos do que vende devagar e constante.

    No caixa, o problema é outro: velocidade. Uma fila de seis pessoas às 18h faz o cliente largar o carrinho e ir ao concorrente. Sistemas de PDV tradicionais custam caro, exigem instalação, travam quando a internet cai e cobram por terminal. O mercadinho acaba com uma calculadora e um caderno — e a diferença de caixa aparece no fim do dia sem explicação.

    As três perdas do varejo alimentar

    Ruptura — o produto acabou e o cliente foi embora; a venda perdida não aparece em relatório nenhum. Quebra — o produto venceu na prateleira e virou prejuízo integral. Diferença de inventário — o estoque diz 40 e existem 31; a diferença some sem registro. Um sistema que ataca essas três já paga a própria assinatura.

    Seção 02Público-alvo e personas

    O produto atende minimercados de bairro com 1 a 3 lojas, faturamento mensal entre R$ 80 mil e R$ 500 mil, de dois a seis funcionários e um ou dois caixas por loja. É o comerciante que hoje não usa sistema nenhum ou usa um sistema antigo que ninguém consegue mais atualizar.

    Seção 03Escopo do MVP

    O MVP resolve o ciclo comprar → precificar → vender → repor. É um ciclo maior que o das outras duas opções, e por isso o roadmap é mais longo.

    Entra na primeira versão

    • Cadastro de produtos com código de barras (GTIN/EAN), unidade de venda (unidade, quilo) e estoque mínimo.
    • Frente de caixa — leitura por código, quantidade, cancelamento de item, subtotal e formas de pagamento (dinheiro, cartão, Pix), com cálculo de troco.
    • Estoque por lote e validade, com baixa automática pela regra FEFO.
    • Entrada de compra — lançamento de nota do fornecedor, atualização do custo médio e sugestão de preço pela margem.
    • Alertas — produtos abaixo do mínimo e lotes vencendo em até 15 dias.
    • Fechamento de caixa — abertura, sangria, suprimento e conferência de diferença.
    • Relatórios — vendas por período, curva ABC de produtos e ranking de margem.
    • Multi-tenant — cada mercado enxerga somente os próprios dados; assinatura por loja e por PDV.

    Fica fora do MVP

    • Emissão de cupom fiscal (NFC-e/SAT). Exige certificado digital, homologação estadual e não se resolve em uma sprint — entra na fase 2, com integração a um emissor especializado.
    • Balança integrada por protocolo serial: o MVP aceita digitação do peso e leitura de etiqueta de balança.
    • E-commerce, delivery e aplicativo do cliente final.
    • Programa de fidelidade e clube de descontos.
    • Conciliação bancária automática das maquininhas.
    Sobre a emissão fiscal

    Vender sem emitir documento fiscal não é opção legal para o cliente. A estratégia do MVP é registrar a venda corretamente desde o primeiro dia e deixar a emissão para uma integração — quando ela chegar, todo o histórico já está estruturado para ser transmitido. Um sistema que registra mal a venda nunca conseguirá emitir bem o documento.

    Seção 04Modelo de dados

    Duas decisões de modelagem definem este projeto. A primeira: toda entidade carrega o identificador do tenant — sem isso, uma consulta esquecida mostra o estoque de um mercado para outro. A segunda: estoque não é um número no produto, é a soma dos lotes — sem lote não há controle de validade, e sem validade não há controle de quebra.

    Seção 05Regras de negócio

    Regra 1 — Preço formado pela margem

    Como no projeto moveleiro, o erro clássico é confundir markup com margem. No varejo alimentar, onde a margem líquida é de 2%, esse erro não é acadêmico: é a diferença entre lucro e prejuízo.

    regra-preco.js 
    function precoPelaMargem(custo, margemAlvo) {
    if (margemAlvo <= 0 || margemAlvo >= 1) { return custo }
    return custo / (1 - margemAlvo)
}

function margemReal(preco, custo) {
    if (preco <= 0) { return 0 }
    return (preco - custo) / preco
}

function arredondarVarejo(valor) {
    // O varejo trabalha com precos terminados em 9: 5,99 em vez de 5,97
    const inteiro = Math.floor(valor)
    const centavos = valor - inteiro
    if (centavos <= 0.49) { return inteiro + 0.49 }
    if (centavos <= 0.79) { return inteiro + 0.79 }
    return inteiro + 0.99
}

    Regra 2 — Baixa de estoque em FEFO

    FEFO — first expired, first out — significa que sai primeiro o lote que vence primeiro, e não o que chegou primeiro. É a regra que evita a quebra: o iogurte do fundo da geladeira precisa sair antes do que acabou de chegar. A venda pode consumir mais de um lote.

    regra-fefo.js 
    function baixarEstoqueFEFO(lotes, quantidade) {
    // Ordena por validade crescente: vence antes, sai antes
    const fila = lotes.slice().sort(function (a, b) {
        return a.validade < b.validade ? -1 : 1
    })

    let restante = quantidade
    let custoTotal = 0
    const consumo = []

    for (let i = 0; i < fila.length; i++) {
        if (restante === 0) { break }

        const lote = fila[i]
        const retirar = Math.min(lote.quantidade, restante)

        if (retirar > 0) {
            lote.quantidade = lote.quantidade - retirar
            restante = restante - retirar
            custoTotal = custoTotal + retirar * lote.custo
            consumo.push({ lote: lote.numero, qtd: retirar, validade: lote.validade })
        }
    }

    return {
        atendido: quantidade - restante,
        faltou: restante,
        custoTotal: custoTotal,
        consumo: consumo
    }
}

    Regra 3 — Alerta de validade e sugestão de liquidação

    Produto que vence em poucos dias tem duas saídas: vender com desconto ou virar prejuízo integral. A regra classifica os lotes por urgência e sugere o desconto que ainda preserva o custo.

    regra-validade.js 
    function diasAteVencer(validade, hoje) {
    const umDia = 1000 * 60 * 60 * 24
    return Math.round((new Date(validade) - new Date(hoje)) / umDia)
}

function classificarLote(dias) {
    if (dias < 0)   { return "VENCIDO" }
    if (dias <= 3)  { return "CRITICO" }
    if (dias <= 15) { return "ATENCAO" }
    return "NORMAL"
}

function descontoSugerido(situacao, preco, custo) {
    if (situacao === "VENCIDO") { return null }

    let desconto = 0
    if (situacao === "CRITICO") { desconto = 0.40 }
    else if (situacao === "ATENCAO") { desconto = 0.15 }
    else { return null }

    let precoPromo = preco * (1 - desconto)

    // Nunca abaixo do custo: melhor girar no minimo do que dar prejuizo
    if (precoPromo < custo) { precoPromo = custo }

    return precoPromo
}

const hoje = "2026-08-11"
const estoque = [

    Regra 4 — Curva ABC

    A curva ABC ordena os produtos pela participação no faturamento e revela onde está o negócio de verdade: cerca de 20% dos itens costumam responder por 80% das vendas. Esses itens nunca podem faltar; os da faixa C podem ter o espaço de gôndola revisto.

    regra-curva-abc.js 
    function curvaABC(vendas) {
    const ordenado = vendas.slice().sort(function (a, b) {
        return b.faturamento - a.faturamento
    })

    let total = 0
    ordenado.forEach(function (v) { total = total + v.faturamento })

    let acumulado = 0
    const resultado = []

    for (let i = 0; i < ordenado.length; i++) {
        acumulado = acumulado + ordenado[i].faturamento
        const percAcumulado = acumulado / total

        let classe = "C"
        if (percAcumulado <= 0.80) { classe = "A" }
        else if (percAcumulado <= 0.95) { classe = "B" }

        resultado.push({
            produto: ordenado[i].produto,
            faturamento: ordenado[i].faturamento,
            participacao: ordenado[i].faturamento / total,
            acumulado: percAcumulado,
            classe: classe
        })
    }

    return resultado
}

    Seção 06Protótipo básico

    O protótipo é uma frente de caixa funcional com catálogo, carrinho, pagamento e baixa de estoque em FEFO. Ao fechar a venda, o estoque é debitado lote a lote e o painel lateral mostra os alertas de validade e de estoque mínimo recalculados na hora.

    Executar

    Frente de caixa

    Abra em projetos/saas-mercado/index.html. Digite o código de barras ou clique no produto do catálogo — o comportamento simula o leitor.

    Abrir o protótipo

    O que o protótipo demonstra

    • Registro de venda por código de barras, com quantidade e cancelamento de item.
    • Baixa FEFO real: a venda mostra de quais lotes saiu cada unidade.
    • Cálculo de troco e conferência do total recebido.
    • Alertas de validade e de estoque mínimo atualizados a cada venda.
    • Resumo do turno com faturamento, custo das vendas e margem apurada.

    O que ele deliberadamente não faz

    • Não emite documento fiscal — a venda é apenas registrada.
    • Não separa tenants: o protótipo simula uma única loja.
    • Não sincroniza entre dispositivos; tudo vive no navegador que o abriu.

    Seção 07Arquitetura e tecnologia

    Duas exigências moldam a arquitetura: o caixa não pode parar quando a internet cai e os dados de um mercado jamais podem vazar para outro.

    CamadaEscolhaPor quê
    PDVAplicação web instalável (PWA) com IndexedDB e service workerFunciona sem rede e atualiza sozinha, sem visita técnica em cada loja
    RetaguardaReact ou VueTelas de cadastro, compras e relatórios com muito estado e filtro
    APINode.js com Express, autenticação por tokenMesma linguagem do front; o token carrega o tenant do usuário
    BancoPostgreSQL com schema por tenantIsolamento forte sem manter um servidor por cliente; backup e restauração por loja
    SincronizaçãoFila de vendas pendentes com identificador único gerado no PDVEvita venda duplicada quando a rede volta e o envio é repetido
    CobrançaAssinatura mensal por loja + adicional por PDVPreço acompanha o tamanho do cliente e o custo de suporte
    Isolamento entre tenants

    Em um SaaS, a falha mais grave não é o sistema cair — é o cliente A enxergar o dado do cliente B. Toda consulta precisa do filtro de tenant aplicado na camada de acesso a dados, nunca dependendo de o programador lembrar de escrevê-lo na tela. Um WHERE esquecido em uma única consulta compromete a plataforma inteira.

    Seção 09Riscos e indicadores

    Riscos

    • Cadastro inicial travando a adoção. Digitar 3 mil produtos é inviável. Mitigação: importação por planilha e base pública de GTIN para preencher a descrição a partir do código de barras.
    • Lentidão no caixa. Se a leitura demorar mais de 300 ms, a operadora abandona o sistema. Mitigação: catálogo inteiro em memória no PDV, busca por índice de código.
    • Divergência de estoque em pouco tempo. Toda saída não registrada (consumo interno, quebra, furto) corrói a confiança no saldo. Mitigação: telas rápidas de quebra e consumo interno, e inventário cíclico por categoria.
    • Concorrência estabelecida. O mercado de PDV é maduro. Mitigação: preço acessível, instalação em minutos e foco em validade e margem — justamente onde o concorrente barato não entrega.

    Indicadores de sucesso

    • Tempo médio por item no caixa, abaixo de 2 segundos.
    • Percentual de quebra por vencimento sobre o faturamento, com meta de queda pela metade em três meses.
    • Itens classe A em ruptura no dia, tendendo a zero.
    • Diferença de caixa por turno, em valor absoluto.
    • Retenção de assinantes ao final de 6 meses.
    Exercício de projeto

    Sugestão de compra por cobertura

    Some as vendas dos últimos 30 dias de cada produto, calcule a média diária e divida o estoque atual por essa média: o resultado é a cobertura em dias. Se a cobertura for menor que o prazo de entrega do fornecedor mais uma folga de segurança, o item entra na lista de compra com a quantidade sugerida. É um exercício de arrays, laços e média — e é a funcionalidade que o dono do mercado mais pede depois que começa a usar o sistema.
